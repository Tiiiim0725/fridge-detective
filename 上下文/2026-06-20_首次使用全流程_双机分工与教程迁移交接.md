## 0. 给接手同学与 Codex 的初始化指令

你现在参与的是「冰箱侦探 / Fridge Detective」主项目的首次使用全流程集成。开始工作前必须完整阅读本文，不要只根据某个页面文件猜测产品结构。

本阶段由两台电脑并行开发：

- 同学电脑负责推荐首页和菜谱详情。
- 用户电脑负责身份启动、Profile、冰箱识别、私人冰箱、Cooking Tutorial Lab 核心迁移和最终串接。
- 推荐 UI 先合并，完整集成随后合并。
- 串接后的联调与 Bug 修复由两个人共同承担，但用户电脑控制最终集成基线、合并顺序和完整回归。

必须遵守：

1. 页面层不直接调用 `supabase.from(...)`，所有数据访问经过 services。
2. 不在前端、文档、提交记录中放 OpenRouter key、service role key、数据库密码或其他 secret。
3. 不另做一套逐步做饭教程。Cooking Tutorial Lab 已经承担教程体验实验。
4. 不让主 App 同时连接主项目与 Lab 两个 Supabase。
5. 不直接复制 Lab 的实验性宽松 RLS 到主项目。
6. 不在两台电脑上同时修改同一个文件，也不要共同直接推送同一个集成分支。
7. 不重写已经跑通的 Profile、Fridge、Ingredient、Recipe、Recommendation services。
8. 未检查 migration list 和 dry-run 前，不执行正式 `supabase db push`。

## 1. 一句话产品目标

本阶段要把已经散落但真实可用的模块连成第一次能给用户完整体验的产品路径：

```txt
启动 App
→ 自动建立匿名用户身份
→ 完成首次 Profile
→ 拍一下冰箱，或暂时跳过
→ 获得个性化推荐
→ 选择一道菜
→ 查看真实菜谱详情
→ 对有精细教程的菜开始逐步跟做
```

当前只为 `tomato_egg_stir_fry / 番茄炒蛋`开放精细跟做教程。其他 199 道菜可以查看真实详情，但不能把当前三步概括伪装成详细教程。

## 4. 主项目与 Lab 的契约差异

迁移前必须理解这些差异，不能直接复制文件后改到能编译就算完成。

### 4.1 Recipe 主表

Lab：

```txt
tutorial_recipes
recipeKey
servings
totalMinutes
difficultyKey = easy
日期为 string
```

主项目：

```txt
recipes
recipeKey
servingCount
totalTimeMinutes
difficultyKey = beginner | normal | confident
日期为 Date
```

结论：主项目的 `recipes` 是唯一菜谱主表。禁止在主项目再建 `tutorial_recipes`。

### 4.2 Steps

Lab `tutorial_steps` 具有：

- 6 条番茄炒蛋详细步骤。
- `action_key`。
- `assistant_context`。
- 详细 ingredient/equipment keys。

主项目 `recipe_steps` 具有：

- 每道菜当前 3 条概括步骤。
- `title/body/estimated_minutes/timer_seconds/image_url`。
- ingredient/equipment keys。
- `tips`。
- 没有 `action_key`。
- 没有 `assistant_context`。

结论：不要覆盖或改写现有 `recipe_steps`。精细教程使用独立增强表，并关联现有 `recipes.id`。

### 4.3 Session 与用户隔离

Lab 的 `cooking_sessions` 没有 `user_id`，RLS 允许 anon/auth 广泛读写。

主项目必须：

- 写入 `user_id = authUser.userId`。
- references `auth.users(id)`。
- select/update 过滤当前用户。
- 通过 `ensureAuthUser()` 获取身份。

### 4.4 AI 与照片

Lab 已有：

- `cooking_ai_questions`。
- `cooking-question-photos`。
- `ask-cooking-helper`。

这些本轮不迁入主项目。保留 Lab 成果，待教程核心稳定后作为下一阶段迁移。

### 4.5 Native Voice

Lab 使用主项目当前没有的原生依赖与配置，包括：

- `expo-dev-client`
- `expo-speech`
- `expo-speech-recognition`
- Picovoice/Porcupine packages
- `expo-build-properties`
- config plugin 和 EAS 配置

这些依赖会改变主 App 原生构建方式，本轮禁止提前带入。

### 4.6 已对齐部分

主项目 006/007/008 之后，Lab 使用的主要 ingredient keys 和 equipment keys 已基本进入主项目正式契约，例如：

- `egg`

```txt

→ onboardingStatus = in_progress
```

不能一开始就写 completed，否则中途失败后用户刷新会被错误跳过 onboarding。

保存成功后：

- 主按钮：`拍一下冰箱`
- 次按钮：`先看看推荐`

### 5.3 Fridge

正式链路继续复用现有真实 services，不退回 mock：


确认成功后首页重新读取推荐，并提示：

### 8.2 下一阶段复扫对账

当前确认逻辑只会新增或刷新本次识别项，不会处理“上次有、本次没看到”。

后续目标：

```txt
本次识别到
+ 上次 active 但本次没看到
→ 用户逐项确认仍在/已没有
→ 再统一更新库存和推荐
```

原则：

- 上次食材默认仍在。
- 不能因为这次没拍到就自动删除。
- 用户明确选择“不在了”后才写 removed。
- 本轮不提前建立 inventory event/history 表。
- 是否做完整历史、识别率和变化日志，在复扫方案中单独设计。

同学开发：

- 推荐首页。
- 菜谱详情。

用户电脑开发：

- 首次使用与导航。
- Profile/Fridge 正式页面。
- 私人冰箱。
- 教程核心迁移。

### Node 3：同学 UI PR

同学完成后运行：

```bash
npx tsc --noEmit
git diff --check
git status --short
```

并验证：

- 首页读取真实推荐。
- 卡片点击进入真实详情。
- 无图片时有正常占位。
- 不显示 raw key。
- 没有 Tutorial 重复实现。

然后先合并同学 PR。

### Node 4：集成分支同步

用户电脑：

1. 拉取已包含同学 UI 的最新 develop。
2. 将集成分支 rebase 或更新到最新 develop。
3. 接上首页到 Fridge、详情到 Tutorial 的正式路由。
4. 处理顺序合并产生的少量 UI 接口差异。

### Node 5：完整串接验证

用户电脑跑首次全流程，并形成 Bug 清单。

### Node 6：两人共同修 Bug

采用：

```txt
共同修复，主电脑整合
```

两个人都参与修复，不限制同学只能修推荐域。

协作规则：

1. 以用户电脑上的最新集成 SHA 作为每轮基线。
2. 每个问题标记 owner 和涉及文件。
3. 两个人从同一 SHA 建独立短修复分支。
4. 同时工作的两个任务不得修改同一文件。
5. 一个问题可以跨模块，但必须先确定主责任人。
6. 修复通过自己的局部测试后创建小 PR 或交付明确 commit。
7. 用户电脑按依赖顺序合并。
8. 每合并一批修复，重新执行完整链路。
9. 若新修复引发回归，回到问题分配，不在同一文件上双线抢修。

建议修复分支命名：

```txt
fix/e2e-<short-problem-name>
```

### Node 7：最终集成 PR

满足全部验收后，集成分支最后合并进入 develop。

## 11. Bug 归属建议

默认归属不是硬限制，而是减少重复排查的起点。

同学优先处理：

- 推荐首页渲染。
- 推荐卡片。
- 推荐结果文案。
- 详情页显示。
- Recipe 数据映射在 UI 中的使用。

用户电脑优先处理：

- Auth/session bootstrap。
- Onboarding guard。
- Profile 保存与跳转。
- Fridge Recognition 和确认。
- Pantry/Fridge 分流。
- Tutorial 与 cooking session。
- 总导航与跨页面刷新。

跨领域问题示例：

- 冰箱更新后推荐不刷新：先由用户电脑定位是导航焦点、缓存还是推荐 service，再分派。
- 推荐卡片能打开详情但 recipeKey 错：同学修 UI 路由参数。
- 详情正确但教程可用性错误：用户电脑修 tutorial service。
- raw ingredient key 出现在首页：同学修展示；若 service 缺少必要字典能力，再共同确认接口。

## 12. 完整验收脚本

### 12.1 新用户首次流程

使用新浏览器 session 或清理站点 session：

1. 打开 `/`。
2. 自动创建 Supabase anonymous user。
3. 自动进入 onboarding。
4. 填写 Profile、偏好、厨具和 pantry。
5. 保存成功，不出现技术错误。
6. 选择“拍一下冰箱”。
7. 拍照/选图并完成识别。
8. 用户确认食材和 pantry 分流。
9. 返回推荐首页。
10. 首页显示“冰箱已更新，推荐已刷新”。
11. 推荐结果基于真实当前用户数据。
12. 点击番茄炒蛋。
13. 进入真实详情。
14. 点击开始跟做。
15. 进入 6 步精细教程。
16. 前进、后退、离开。
17. 再次进入后恢复步骤。
18. 完成教程，session 为 completed。
19. 进入“我的”。
20. 能看到 Profile 和私人冰箱入口。
21. 私人冰箱展示当前 active items。
22. 刷新 App 后不重新进入 onboarding。

### 12.2 跳过冰箱

1. 完成 Profile。
2. 选择“先看看推荐”。
3. 首页仍能基于 Profile/Pantry 生成推荐。
4. 用户可以之后从中间 Tab 或首页更新冰箱。

### 12.3 非教程菜品

1. 打开没有精细教程的任意 Recipe。
2. 正常显示真实详情和三步概括。
3. 不出现可点击的“开始跟做”。
4. 可以显示克制的“精细教程准备中”。

### 12.4 错误状态

验证：

- Supabase 配置错误。
- Anonymous Sign-in 失败。
- Profile 部分保存失败。
- 推荐无结果。
- 图片上传失败。
- AI 识别失败。
- 没有字典匹配项。
- Tutorial seed 缺失。
- Session 更新失败。

错误文案必须面向用户，debug 详情只进入折叠区或开发日志。

### 12.5 技术检查

每个 PR 至少运行：

```bash
npx tsc --noEmit
git diff --check
git status --short
```

最终还需检查：

- 页面没有 `supabase.from(...)`。
- 没有 secret。
- 没有指向 Lab Supabase。
- 没有重复 Recipe 表。
- 没有把 Lab native voice 依赖带入主项目。
- 桌面 Web 和约 `390 x 844` 移动视口无重叠和溢出。

## 13. 数据库操作边界

教程 migration 准备完成后，必须按顺序：

```bash
supabase migration list
supabase db push --dry-run
```

只有待应用 migration 与预期完全一致时，才由用户明确允许正式 push。

教程 seed 单独检查并手动执行，不能借机重跑 Recipe v0.2 大 seed。

严禁：

- `supabase db reset`
- 未检查待应用列表就 push
- 将 Lab Supabase link 复制到主项目
- 将实验 RLS 原样投入主库

## 14. 同学每次交付必须提供的信息

同学或其 Codex 每次提交/PR 后必须汇报：
