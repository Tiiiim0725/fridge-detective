# Fridge Recognition 北极星体验：饿了就拍一下，推荐立刻变准

## 1. 一句话目标

用户有点饿了，打开 App，先看到基于当前冰箱记录生成的菜谱推荐；如果用户觉得冰箱记录可能不准，可以快速拍几张冰箱照片，AI 识别出食材草稿，用户一键确认后更新冰箱内容，并立刻回到更准确的菜谱推荐。

这个模块的目的不是“为了识别而识别”，而是让用户在 30-60 秒内完成一次冰箱状态更新，并马上得到更可信的晚餐推荐。

---

## 2. 目标使用场景

用户下课、下班或回到家，感觉有点饿，但不想认真整理冰箱，也不想打开外卖软件乱刷。

用户打开「冰箱侦探」App。

首页直接展示一些菜谱推荐，这些推荐来自系统已有的冰箱库存记录、用户偏好、厨具条件和菜谱库。

用户突然想到：“我冰箱里好像还有别的东西，或者上次记录已经不准了。”

用户点击首页上的“更新冰箱”或“拍一下冰箱”。

进入拍照识别页面后，屏幕上出现轻量引导文案，例如：

> 请依次拍摄冰箱里的主要隔层，拍清主要食材即可。

用户打开相机，依次拍摄冰箱隔层。每拍完一张，照片会缩小成缩略图，出现在页面旁边或底部。刚拍完的照片默认被选中。用户可以点选缩略图查看，也可以删除明显拍糊或不想参与识别的照片。

用户拍完后点击中间拍照按钮旁边的确认勾，结束拍摄并进入识别。

识别过程中，页面进入“正在识别你的冰箱”状态。

识别完成后，当前页面背景模糊并调暗，浮层展示 AI 发现的食材候选。食材以图标 / chip / 卡片形式横向或网格排列，例如：

> 鸡蛋 ✓　牛奶 ✓　黄瓜 ✓　生菜 ✓　奶酪 ✓

默认所有识别项都被选中。用户可以取消误识别的食材，也可以简单修改或删除不确定的项。

用户点击：

> 更新冰箱并推荐菜谱

系统把用户确认后的食材写入正式冰箱库存记录，并跳转回菜谱推荐页。

推荐页刷新，展示基于最新冰箱内容的菜谱推荐。

## 3. 页面体验状态机

### State A：首页推荐状态

用户看到菜谱推荐。

页面核心内容：

- 推荐菜谱卡片
- 当前冰箱记录的简短提示
- “更新冰箱”入口

用户动作：

- 直接查看菜谱
- 点击“更新冰箱”进入拍照识别

技术对应：

- 后续读取 `fridge_items`
- 后续读取 recipe recommendation result
- 暂时可用 mock recommendation 或已有 recipeService 结果占位

---

### State B：拍照引导状态

用户进入拍照识别页。

页面核心内容：

- 相机画面或 dev 阶段的 image URL 输入
- 当前拍摄引导句
- 拍照按钮
- 已拍照片缩略图列表
- 完成 / 打勾按钮

引导文案原则：

- 不让用户觉得必须严格完成复杂盘点
- 强调“拍清主要食材即可”
- 分区逻辑存在，但体验上保持轻量

可选 zone：

- `fridge_top`
- `fridge_middle`
- `fridge_bottom`
- `fridge_door`
- `fridge_drawer`
- `fridge_extra`

技术对应：

- 正式版使用相机 / 图片选择
- dev 版可先用多个 image URL 模拟多张照片
- 每张照片对应一条 `fridge_scan_photos`
- 每次识别属于一个 `fridge_scan`

---

### State C：多图缩略图状态

用户已经拍摄一张或多张冰箱照片。

页面核心内容：

- 缩略图胶片条
- 当前选中照片预览
- 删除 / 取消某张图
- 继续拍照
- 完成拍摄并开始识别

用户感受目标：

- 用户知道自己已经拍了哪些图
- 用户有控制感
- 用户可以去掉明显不好的照片

技术对应：

- 前端维护本地 `selectedPhotos`
- 每张 photo 有 local uri / remote storage path / zoneKey / status
- 识别前可选择哪些照片参与本次 scan

---

### State D：识别中状态

用户结束拍摄后，系统开始识别。

页面核心内容：

- 背景保持照片或页面内容，但模糊 / 变暗
- 文案：正在识别你的冰箱
- 可显示进度：正在识别第 1 / 3 张

技术对应：

- 调用 `fridgeRecognitionService`
- 内部串联：
  - 创建 scan
  - 上传照片或接收 imageUrl
  - 记录 photo
  - 调用 `aiService.recognizeFridgePhoto()`
  - 保存识别草稿到 `fridge_scan_items`

---

### State E：识别结果确认状态

AI 返回识别结果后，用户看到食材候选。

页面核心内容：

- 食材 chip / icon / card
- 默认全选
- 用户可取消误识别项
- 用户可简单编辑名称 / 数量
- 不确定项视觉上弱提示，例如“待确认”

文案示例：

> AI 发现了这些食材，请确认一下。

候选卡片示例：

- 鸡蛋 × 10 ✓
- 牛奶 × 1 ✓
- 黄瓜 × 5 ✓
- 酸奶 × 2 ？
- 瓶装水 × 4，可默认降低优先级或过滤

技术对应：

- `fridge_scan_items` 是 AI 草稿表
- `needs_review=true` 的 item 前端需要弱提示
- 用户取消选择的 item 不进入正式 `fridge_items`
- 用户确认的 item 才写入正式库存

---

### State F：确认更新状态

用户点击确认按钮。

按钮文案建议：

> 更新冰箱并推荐菜谱

而不是：

> 保存识别结果

技术对应：

- 把选中的 `fridge_scan_items` 写入 / 合并到 `fridge_items`
- scan 状态更新为 completed / confirmed
- 跳转或返回推荐页
- 推荐页重新读取最新 fridge items

---

### State G：推荐刷新状态

用户回到首页 / 推荐页。

页面核心内容：

- 推荐菜谱刷新
- 可显示轻提示：

  > 已根据刚刚识别的食材更新推荐

体验目标：

用户感受到刚刚拍照带来了直接收益：推荐变准了。

技术对应：

- 推荐模块读取最新 `fridge_items`
- 后续组合 `profileService`、`fridgeService`、`recipeService`
- 第一版可以先规则推荐 top 8

---

## 4. 技术倒推原则

之后每个技术任务都必须能对应到这个体验链路中的某个状态。

### 必须优先支持的技术能力

1. 单张图片识别
   已完成：OpenRouter + Edge Function 已能返回结构化 JSON。

2. 多图输入
   用户一次可能拍多张，不能只按单图设计最终体验。

3. scan / photo / scan_items 草稿结构
   AI 识别结果必须先进入草稿，不直接写正式库存。

4. 用户确认
   用户确认后的 item 才进入 `fridge_items`。

5. 推荐刷新
   拍照识别完成后的真正收尾不是“识别成功”，而是“推荐变准”。

---

## 5. 当前 dev 页面的方向

`/dev-fridge-recognition-check` 不应只是一个工程调试页：

> 输入 URL → 输出 JSON

它应该尽量成为正式流程的简化雏形：

> 输入多张图片 URL
> 模拟多张拍照缩略图
> 点击开始识别
> 展示食材候选 chip
> 默认全选
> 用户取消部分食材
> 点击确认
> 写入 fridge_scan_items / fridge_items
> 显示可进入推荐页的结果

dev 阶段可以暂时不用真实相机和 Storage，但页面逻辑要向最终体验靠拢。

---

## 6. 暂时后置的优化

以下问题重要，但不要在主链路完成前过度消耗时间：

- 模糊 / 太暗 / 遮挡场景优化
- 补拍 / 重拍策略
- bbox / region 可视化
- 更复杂的 item 标准化
- 水瓶、包装物、非食材过滤
- confidence 精细调校
- 多模型对比
- 完整正式 UI 动效

当前优先级是：

> 真实识别 → 草稿展示 → 用户确认 → 正式库存 → 推荐刷新
