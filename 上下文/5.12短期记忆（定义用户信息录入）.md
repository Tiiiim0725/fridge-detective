## 2. 关键架构决策：采用 Supabase Anonymous Auth

### 2.1 决策内容

项目确认采用 Supabase Anonymous Auth 来承接首次未注册体验。

用户首次打开 App 时：

```txt
App 启动
-> authService.ensureAuthUser()
-> 如果没有 session，则 signInAnonymously()
-> 获得 auth.users.id
-> 所有私有业务数据都绑定这个 user_id
-> 用户完成第一次做饭后，再绑定邮箱 / 手机 / OAuth
```

### 2.2 为什么不用 guest_id

不设计 guest_id，也不让业务主表长期存在 user_id nullable。

原因：

1. RLS 会更干净。
2. Storage 路径和权限会更清楚。
3. 后续用户绑定正式账号时，不需要把匿名数据迁移到另一个 user_id。
4. 前端、services、数据库都能统一使用 auth.users.id。
5. 避免 guest_id、device_id、本地缓存、正式 user_id 多套身份系统互相打架。

### 2.3 本地存储的新定位

AsyncStorage 不再作为正式业务数据归属层。

新的定位：

```txt
AsyncStorage = 草稿缓存 / 离线容错 / 未提交表单状态
Supabase = 正式私有业务数据
Anonymous Auth user_id = 未注册用户的数据归属身份
正式注册 = 绑定登录方式，不是迁移数据到新账号
```

### 2.4 对长期上下文文档的影响

长期文档中所有“信息先本地存储，注册后迁移到账户”的旧表达，都应该改为 Anonymous Auth 逻辑。

推荐替换表述：

```txt
首次体验尽量零摩擦。用户首次打开 App 时通过 Supabase Anonymous Auth 自动获得 auth.users.id，口味偏好、厨房设备、常备调料、冰箱记录等正式私有业务数据归属该 user_id。AsyncStorage 只用于草稿缓存、离线容错和未提交表单状态。用户完成第一次做饭后，再引导绑定邮箱 / 手机 / OAuth，将匿名账号升级为正式账号，而不是迁移本地数据到新账号。
```

这不是让页面团队独立开发完整业务，而是在统一架构下，为某个基础模块同时设计：

```txt

```

### 3.2 第一条切片



### 3.3 受控纵向切片必须遵守的规则

1. 页面不直接访问 Supabase。
2. 页面只能调用 services。
3. 私有数据必须绑定 auth.users.id。

6. 不允许只做 UI、不允许只建表、不允许每个人各写各的 Supabase 查询。

## 4. User Profile Module 的产品定位

User Profile / Onboarding Foundation 不是泛化用户画像模块。

它的核心价值是给推荐算法提供稳定输入。

具体包括：

```txt
口味偏好
菜系偏好
做饭风格
普通忌口
过敏项
厨房设备
常备调料 / 干货 / 基础主食
```

这些数据主要用于：

1. 菜谱推荐算法打分。
2. 菜谱硬过滤，例如过敏项、明确不吃的食材。
3. 推荐理由展示，例如“你有平底锅、鸡蛋、酱油，且符合简单快手偏好”。
4. 后续 onboarding 页面预填、编辑、保存。

核心原则：

```txt
所有会进入推荐算法的用户输入，都应尽量是选项、枚举、数值或标准 key，不使用自由文本作为推荐依据。
```

## 6. Step 2 已完成：数据库字段设计

需要创建四张表：

```txt
profiles
user_preferences
kitchen_equipment
pantry_items
```

### 6.1 通用设计原则

1. 所有表启用 RLS。
2. profiles.id 直接等于 auth.users.id。
3. 其他私有表使用 user_id references auth.users(id)。
4. 用户只能访问自己的数据。
5. 不存中文 label。
6. 不存可由 key dictionary 推导出的展示名称。
7. kitchen_equipment 和 pantry_items 只存用户拥有的 key，不存 false 行。
8. user_preferences 的单选字段允许 null，用于区分未填写和用户明确选择。
9. 多选字段使用 text[]，默认空数组。

### 6.2 profiles

用途：用户业务侧基础档案表。

字段：

```txt
id uuid primary key references auth.users(id) on delete cascade
display_name text null
avatar_url text null
onboarding_status text not null default 'not_started'
onboarding_completed_at timestamptz null
is_anonymous_snapshot boolean not null default true
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

onboarding_status 允许值：

```txt
not_started
in_progress
completed
```

RLS 逻辑：

```sql
auth.uid() = id
```

### 6.3 user_preferences

用途：推荐算法的用户偏好输入表。

一用户一行，unique(user_id)。

字段：

```txt
id uuid primary key default gen_random_uuid()
user_id uuid not null references auth.users(id) on delete cascade
portion_size text null
spice_level text null
saltiness text null
cuisine_preferences text[] not null default '{}'
meal_style_preferences text[] not null default '{}'
diet_tags text[] not null default '{}'
disliked_ingredient_keys text[] not null default '{}'
allergen_keys text[] not null default '{}'
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

约束：

```txt
unique(user_id)
portion_size in small / normal / large or null
spice_level in none / mild / medium / hot or null
saltiness in light / normal / salty or null
数组字段只能包含 v0.1 key dictionary 允许值
no_preference 不能和其他 cuisine key 同时存在
限制数组长度，防止异常输入
```

RLS 逻辑：

```sql
auth.uid() = user_id
```

### 6.4 kitchen_equipment

用途：用户拥有的厨房设备 key。

字段：

```txt
id uuid primary key default gen_random_uuid()
user_id uuid not null references auth.users(id) on delete cascade
equipment_key text not null
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

约束：

```txt
unique(user_id, equipment_key)
equipment_key 必须属于 KitchenEquipmentKey
```

不存：

```txt
equipment_name
category
中文 label
英文 label
false 行
```

分类和 label 放在 types/profile.ts 的 key dictionary。

### 6.5 pantry_items

用途：用户拥有的长期常备调料、干货、基础主食和少量常见囤货。

字段：

```txt
id uuid primary key default gen_random_uuid()
user_id uuid not null references auth.users(id) on delete cascade
pantry_item_key text not null
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

约束：

```txt
unique(user_id, pantry_item_key)
pantry_item_key 必须属于 PantryItemKey
```

不存：

```txt
pantry_item_name
category
中文 label
英文 label
false 行
```

分类和 label 放在 types/profile.ts 的 key dictionary。

### 6.6 updated_at trigger

migration 中建议创建：

```sql
create extension if not exists pgcrypto;

create or replace function public.set_updated_at()
returns trigger
language plpgsql
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;
```

四张表都使用 trigger 自动维护 updated_at。

### 6.7 RLS 总原则

所有表：

```sql
alter table public.<table_name> enable row level security;
```

profiles：

```sql
(select auth.uid()) is not null and (select auth.uid()) = id
```

其他表：

```sql
(select auth.uid()) is not null and (select auth.uid()) = user_id
```

允许用户对自己的数据执行：

```txt
select
insert
update
delete
```

注意：RLS 不区分匿名用户和正式用户，只判断 auth.uid()。

## 8. Step 4 已完成：authService.ts 和 profileService.ts 设计

### 8.1 authService.ts 职责

authService.ts 只负责身份层。

提供：

```ts
ensureAuthUser(): Promise<AuthUserContext>
getCurrentUser(): Promise<AuthUserContext | null>
signOut(): Promise<void>
```

AuthUserContext：

```ts
interface AuthUserContext {
  userId: string;
  email: string | null;
  isAnonymous: boolean;
}
```

ensureAuthUser 内部流程：

```txt
1. supabase.auth.getSession()
2. 如果有 session.user，返回 userId / email / isAnonymous
3. 如果没有 session，调用 supabase.auth.signInAnonymously()
4. 如果失败，throw Error
5. 如果成功但没有 user，throw Error
6. 返回 AuthUserContext
```

authService 不负责：

```txt
创建 profiles
保存 preferences
保存 equipment
保存 pantry
推荐算法
UI 状态
```

### 8.2 profileService.ts 职责

profileService.ts 负责 User Profile / Onboarding Foundation 的业务读写。

提供：

```ts
ensureProfile(): Promise<Profile>
getProfile(): Promise<Profile | null>
updateProfile(input: UpdateProfileInput): Promise<Profile>

getUserPreferences(): Promise<UserPreferences | null>
saveUserPreferences(input: SaveUserPreferencesInput): Promise<UserPreferences>

getKitchenEquipment(): Promise<KitchenEquipmentItem[]>
saveKitchenEquipment(input: SaveKitchenEquipmentInput): Promise<KitchenEquipmentItem[]>

getPantryItems(): Promise<PantryItem[]>
savePantryItems(input: SavePantryItemsInput): Promise<PantryItem[]>

getOnboardingContext(): Promise<OnboardingContext>
```

OnboardingContext：

```ts
interface OnboardingContext {
  profile: Profile;
  preferences: UserPreferences | null;
  equipmentKeys: KitchenEquipmentKey[];
  pantryItemKeys: PantryItemKey[];
}
```

### 8.3 ensureProfile()

语义：

```txt
确保当前 auth user 在 profiles 表中有一行。
```

内部流程：

```txt
1. authService.ensureAuthUser()
2. select profiles where id = authUser.userId
3. 如果存在，返回
4. 如果不存在，insert profiles
5. 如果并发导致 duplicate key，重新 select
```

创建 profile 时默认：

```txt
id = authUser.userId
onboarding_status = not_started
is_anonymous_snapshot = authUser.isAnonymous
```

建议不要用 upsert 覆盖 profile，避免误覆盖已有字段。

### 8.4 getProfile()

语义：只读当前 profile，不自动创建。

如果没有 session 或没有 profile，返回 null。

### 8.5 updateProfile(input)

语义：更新基础 profile。

如果 profile 不存在，先 ensureProfile()。

特殊规则：

```txt
如果 onboardingStatus = completed 且 input 没有显式传 onboardingCompletedAt，service 自动写当前时间。
```

### 8.6 getUserPreferences()

语义：只读当前用户偏好，不自动创建空 preferences。

原因：避免一进 App 就创建空记录，使“用户是否填写过偏好”变得不清楚。

### 8.7 saveUserPreferences(input)

语义：创建或更新当前用户 preferences。

保存策略：

```txt
upsert on user_id
```

原因：user_preferences 与用户一对一，save 的语义就是保存当前状态。

保存前必须做：

```txt
key 校验
数组去重
no_preference 互斥处理
空数组保留为空数组
```

no_preference 处理策略：

```txt
如果 cuisinePreferences 包含 no_preference，则最终保存为 ['no_preference']。
```

### 8.8 saveKitchenEquipment(input)

语义：用当前完整选择替换用户设备集合。

保存策略：

```txt
delete old rows for current user
insert new rows
return latest rows
```

原因：设备数量小，完整替换更清晰。

后续伏笔：


### 8.11 profileService 错误处理原则

```txt
冰箱食材覆盖度
pantry 覆盖度
设备满足度
菜系偏好命中
做饭风格命中
辣度距离
咸淡距离
用时和难度排序
```

重要原则：

```txt
用户偏好、设备、调料不是为了画像好看，而是为了推荐算法稳定消费。
```

## 13. 重要伏笔和后续注意事项

### 13.1 equipment / pantry 保存方式后续可能升级

当前第一版为了简单，采用：

```txt
delete old rows
insert new rows
```

风险：delete 成功但 insert 失败，可能短暂清空用户选择。

当前接受这个风险，因为设备和 pantry 可重新选择，MVP 早期数据量小。

后续如需更强一致性，改为 Postgres RPC：

```txt
replace_kitchen_equipment(keys text[])
replace_pantry_items(keys text[])
```

### 13.2 key dictionary 后续可能拆文件

当前 key dictionary 放在 types/profile.ts。

原因：早期文件少，容易维护。

后续如果变大，可拆到：

```txt
constants/profileKeys.ts
```

### 13.3 types/database.ts 后续由 Supabase 生成

当前 types/profile.ts 是业务层类型。

后续 migration 落地后，再生成：

```bash
supabase gen types typescript --project-id YOUR_PROJECT_ID > types/database.ts
```

不要在 Step 5 一开始就强行依赖完整 database.ts。

### 13.4 菜谱库必须对齐 key dictionary

未来 recipes / recipe_ingredients 字段必须复用这些 key。

尤其注意：

```txt
cuisine_tags 对齐 cuisine_preferences

required_equipment_keys 对齐 kitchen_equipment.equipment_key

spice_level / saltiness 使用同一套 key
allergen_keys 使用同一套 key
```

MVP 不收集：
