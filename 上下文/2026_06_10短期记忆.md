### 4.4 数量字段设计

第一版数量字段采用：

```txt
quantity_kind
quantity_text
quantity_count
```

`quantity_kind`：

```txt
unknown | text | count
```

规则：

```txt
unknown:
  quantity_text = null
  quantity_count = null

text:
  quantity_text 非空，例如“一把”“一罐”“半袋”“少量”“一盒”
  quantity_count = null

count:
  quantity_text = null
  quantity_count 为 >= 0 的 number，例如 3、6、12
```

核心决策：

- AI 可以给数量建议，但只是草稿。
- `fridge_scan_items` 保存 AI 或用户编辑中的草稿数量。
- `fridge_items` 保存用户确认后的正式数量。
- 第一版不使用复杂 `quantity_value / unit_key` 作为识别主结构。
- `quantity_text` 和 `quantity_count` 二选一。

## 6. `supabase/config.toml` 的讨论与决策

### 6.1 它是什么

`supabase/config.toml` 是 Supabase CLI 的项目配置文件，通常由：

```bash
supabase init
```

生成。

它可以配置：

```txt
本地 Supabase 服务
本地数据库端口
Auth 设置
Storage 设置
Edge Function 设置
seed 文件路径
多环境 / preview branch 等
```

它不是数据库，不是密钥文件，不是 migration，也不是 seed 本身。

### 6.2 本轮为什么遇到它

本轮原本想用：

```bash
supabase db push --include-seed
```

执行 seed。但该命令需要从 `supabase/config.toml` 中的 `[db.seed] / sql_paths` 读取 seed 配置。项目里没有 `supabase/config.toml`，无法确认 CLI 会执行哪个 seed 文件。

所以编程 AI 按规则停止，未执行 seed。

### 6.3 当前决策

当前阶段不为了执行一次 seed 临时创建完整 `supabase/config.toml`。

本轮采用 Supabase Dashboard SQL Editor 手动执行 seed。

`supabase/config.toml` 作为后续工程化待办，适合在正式规划这些内容时再做：

```txt
本地 Supabase 环境
seed 自动化
Storage bucket / policy
Edge Function
多环境 dev / staging / production
preview branch
```

## 7. migration / seed / types / services / tsc 的概念对齐

### 7.1 migration

migration 是数据库结构变更记录，回答：

```txt
数据库应该长什么样？
```

它负责创建表、字段、索引、外键、RLS policy、trigger、GRANT 等。

项目例子：

```txt
001_user_profile_module.sql
002_grant_user_profile_permissions.sql
003_recipe_ingredient_foundation.sql
004_fridge_foundation.sql
```

### 7.2 seed

seed 是初始数据 / 样例数据 / 公共基础数据，回答：

```txt
数据库建好以后，里面先放哪些基础数据？
```

项目例子：

```txt
supabase/seeds/recipe_seed_v0.1.sql
```

migration 管结构，seed 管数据。

### 7.3 types

`types/*.ts` 是 TypeScript 类型定义，回答：

```txt
代码里这些数据长什么样？
```

types 是数据库 / service / 页面之间的数据合同，不直接查数据库，不执行业务逻辑。

### 7.4 services

`services/*.ts` 是业务逻辑层，回答：

```txt
某个模块的数据应该怎么读、怎么写、怎么处理？
```

页面不应该直接写：

```ts
supabase.from('fridge_items').insert(...)
```

而应该调用 service。

当前 service 分工：

```txt
authService.ts：当前用户、匿名登录、获取 userId。
profileService.ts：profile / preferences / equipment / pantry。
ingredientService.ts：食材字典读取、raw name → ingredient_key 标准化。
recipeService.ts：recipe / ingredient 公共知识库读取。
fridgeService.ts：fridge_scans / fridge_scan_photos / fridge_scan_items / fridge_items 的 DB 读写闭环。
```

### 7.5 tsc

`tsc` 是 TypeScript 编译器 / 类型检查工具。

当前使用：

```bash
npx tsc --noEmit
```

含义：只检查 TypeScript 类型、导入路径、函数签名、字段名等是否有错误；不生成文件；不运行 app；不修改数据库。

## 10. Fridge Recognition Prototype v0.2 初步边界

### 10.1 阶段目标

下一阶段建议定义为：

```txt
Fridge Recognition Prototype v0.2
```

目标不是一次做完整正式拍照产品，而是做出一个：

```txt
真实图片识别 API 可跑
prompt 可测
输出可验证
能写入 fridge_scan_items
能通过 dev-only 页面单独测试
```

的原型。

### 10.2 暂时不做

Fridge Recognition v0.2 暂不做：

```txt
复杂 bbox / region
补拍逻辑
过期判断
正式 UI
Recommendation / Top 8
完整生产级拍照流程
复杂库存扣减
```

### 10.3 应包含的五块

#### A. API / Edge Function 边界

原则：

```txt
真实 AI API 不进前端。
前端只调用自己的 service。
Claude / 视觉模型调用放在 Supabase Edge Function。
API key 只放 Edge Function 环境变量。
```

需要在新对话中查官方文档确认：

```txt
当前 OpenAI / Claude / 其他视觉模型 API 的图片输入格式、价格、限制；是否支持 URL / base64 / multipart；是否适合 Supabase Edge Function。
```

注意：因为这些 API 能力、价格、模型名可能变化，新对话必须使用 web 查官方文档，不要只凭记忆。

#### B. Storage 与上传链路

规划：

```txt
Storage bucket: fridge-photos
Storage path: {user_id}/{scan_id}/{photo_id}.jpg
```

第一阶段可设计：

```txt
前端拍照或选图
→ 上传 Supabase Storage
→ 上传成功后写 fridge_scan_photos
→ 调用识别 Edge Function
→ 识别结果写 fridge_scan_items
```

但具体是先上传再识别，还是 Edge Function 读取 signed URL / public URL / base64，需要新对话查官方文档后定。

#### C. Prompt 与输出 schema

Prompt 要明确：

- 这是某个冰箱区域的照片。
- 系统已知道 `zone_key` 和 `guide_prompt`。
- 只识别能看清的食材。
- 不要过度猜测。
- 输出严格 JSON。
- 数量使用 `quantity_kind / quantity_text / quantity_count`。
- 不输出 `photo_id` / `scan_id` / `bbox`。
- 不确定时设置 `needs_review` 和 `uncertainty_reason`。
- 输出 raw name 后由 `ingredientService` 标准化，不要求 AI 自己保证 `ingredient_key` 正确。

建议输出结构：

```json
{
  "items": [
    {
      "raw_name": "egg",
      "display_name": "鸡蛋",
      "quantity_kind": "count",
      "quantity_count": 6,
      "quantity_text": null,
      "confidence": 0.86,
      "needs_review": false,
      "uncertainty_reason": null
    }
  ]
}
```

#### D. service 层拆分

当前 `fridgeService.ts` 是 DB 层，不应塞入所有逻辑。

建议后续拆分：

```txt
fridgeService.ts
  继续负责 scan/photo/items/fridge_items 的数据库读写。

aiService.ts
  负责调用 Supabase Edge Function，不直接接触业务表，不放 API key。

fridgeRecognitionService.ts
  负责组织一次识别流程：读取/接收 photo 上下文，调用 aiService，校验输出，保存到 fridge_scan_items。

storageService.ts 或 fridgePhotoService.ts
  负责上传图片到 Supabase Storage，并返回 bucket/path/metadata。
```

不要把 AI 调用、Storage 上传、DB 写入、UI 状态都塞进一个 service。

#### E. dev-only 识图测试页

建议新建：

```txt
/dev-fridge-recognition-check
```

第一阶段功能：

- 选择 / 上传一张测试冰箱图。
- 选择 `zone_key`。
- 调用真实识别 API。
- 展示 AI raw response。
- 展示 normalized result。
- 保存到 `fridge_scan_items`。
- 用户可检查识别是否靠谱。

测试重点：

```txt
真实图片能不能识别？
JSON 稳不稳定？
quantity 输出是否合理？
ingredient_key 标准化是否成功？
needs_review 是否有用？
失败时错误是否可理解？
```

## 11. AI 辅助编程 / 防屎山规则

本轮继续强调了 AI 辅助编程的维护规则。用户希望这一点长期写进项目上下文前部关键位置。

核心判断：

```txt
代码量大不是屎山；
边界不清、重复逻辑、改动不可控才是屎山。
```

文件可以大，但不能杂。

判断代码是否健康，看：

```txt
职责是否明确？
改动是否局部？
输入输出是否稳定？
出错时能不能定位？
能否用 dev 页面验证？
AI 能否被清晰指挥只改局部？
是否有重复逻辑 / 多套真相？
```

项目规则：

- 页面不直接 `supabase.from`。
- 页面只做展示和交互。
- service 是模块边界，不是垃圾桶。
- types/migrations/services 分层明确。
- 每轮 Claude Code 只做一种任务：只读检查 / 只改一个指定文件 / 只运行验证命令。
- 核心文件修改前后都要检查 diff，不只看 git status 文件名。
- 禁止无授权格式化整文件、改风格、重排 import。
- 不允许每个模块自己创建第二套字典 / 第二套查询逻辑。
- Fridge 必须复用 Recipe Foundation 的 `ingredients` 和 `ingredientService`。
