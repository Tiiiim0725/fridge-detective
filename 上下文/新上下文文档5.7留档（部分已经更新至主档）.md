## 3. MVP 产品核心结构

### 区块一：信息录入层（P0 - MVP）

MVP 暂不收集病史、体重、糖尿病等敏感健康信息。

#### MVP 录入内容

第一层：口味偏好

- 辣度：不辣 / 微辣 / 中辣 / 重辣
- 咸淡：清淡 / 正常 / 偏咸
- 饮食风格：中餐 / 西餐 / 韩餐 / 日式 / 简单快手 / 健身轻食等
- 忌口：不吃香菜、不吃葱蒜、不吃海鲜、素食等普通饮食偏好
- 过敏项：可选填，但不做医疗判断，只用于过滤明显冲突食材

第二层：厨房设备与常备调料

- 厨房设备：锅、平底锅、电饭煲、空气炸锅、烤箱、微波炉、刀、砧板、锅铲等
- 常备调料：油、盐、糖、酱油、醋、料酒、胡椒、辣椒粉、蚝油、番茄酱等

#### 关键策略

- 首次体验尽量零摩擦。
- 信息先本地存储，完成第一次做饭后再邀请注册。
- 注册后可将本地偏好、设备、调料、冰箱记录迁移到账户。
- 未来如加入健康信息，必须另设授权、隐私说明、数据最小化与安全存储，不进入当前 MVP。

---

### 区块二：拍照识别层（P0 - MVP）

#### 用户流程

1. 提示用户分层拍摄冰箱，每层单独拍，碗碟内容尽量拍清楚。
2. 用户上传多张照片。
3. AI 识别食材，生成食材清单草稿。
4. 用户确认、手动增删、修正数量或单位。
5. 最终生成本次可用食材清单。

#### MVP 策略

- 先做多图上传 + AI 初识别 + 人工确认。
- 补拍引导放二期。
- 不判断食材是否过期。
- 不直接承诺"能不能吃"。
- 必须保留手动编辑，作为 AI 识别错误的兜底。

#### 关键工程要求

- 每次识别应有 `fridge_scans` 记录。
- 每张图片应有 `fridge_scan_photos` 记录。
- AI 原始输出、置信度、错误信息、用户修正结果都要可追踪。

### 区块三：后台菜品库（P0 - MVP，离线预建）

#### 菜品字段

- 菜名
- 简介
- 所需食材
- 最低食材集合
- 可替代食材
- 所需厨具
- 所需调料
- 总用时
- 难度
- 口味标签
- 菜系标签
- 适合场景
- 步骤教程
- 关键步骤配图
- 菜品卡片图

#### 菜品数量分阶段

| 阶段 | 数量 | 目的 |
|---|---:|---|
| Alpha | 20-30 道 | 验证字段结构、匹配逻辑、教程展示 |
| Closed Beta | 50-80 道 | 验证用户选择和做饭完成率 |
| Public MVP | 100-150 道 | 覆盖基础家常场景 |
| 后续扩展 | 200-300 道 | 内容规模化 |

当前不要被 200-300 道目标拖慢。先做 20-30 道高质量结构化测试菜。

---

### 区块四：匹配与轮盘展示（P0 - MVP）

#### 匹配逻辑

输入：

- 用户确认后的冰箱食材
- 厨房设备
- 常备调料
- 口味偏好
- 菜品库字段

输出：

- 最多 8 张推荐菜品卡片
- 每张卡片显示：菜名、总用时、难度、已有食材覆盖度、缺少食材、推荐理由

#### MVP 匹配策略

先用纯代码规则匹配，不让 AI 现场生成菜谱：

- 必需食材覆盖度
- 可替代食材覆盖度
- 调料是否具备
- 厨具是否具备
- 口味偏好匹配度
- 用时与难度排序

AI 只负责识别冰箱和后续成品评分；菜谱推荐先用本地规则，降低成本与不可控性。

---

### 区块五：时间轴烹饪教程（P1 - 简版先上）

- 展示菜品详情卡片：总用时、食材清单、缺少食材、难度。
- 时间轴步骤教程：文字 + 关键步骤配图。
- 步骤逐步推进。
- 语音播报、计时器、并行步骤优化放二期。

---

### 区块六：打分与成就海报（P1）

- 用户拍摄成品照片。
- AI 打分维度：颜值、摆盘、挑战难度。
- 评分策略偏慷慨，尤其是新用户首次完成做饭。
- 解锁称号，更新侦探档案。
- 生成"侦探结案报告"风格成就海报。
- 支持保存和分享。

---

### 区块七：食材消耗追踪（P2）

- 做完饭后自动扣除已用食材，更新冰箱食材库。
- 用户可手动调整扣除结果。
- 长期积累后，AI 对用户冰箱状态的认知更准确。
- 该模块是留存机制，但不进入第一轮 MVP 主链路。

## 4. 技术栈决策

| 层级 | 选型 | 当前状态 / 理由 |
|---|---|---|
| 前端框架 | React Native + Expo | 一套工程支持 iOS / Android；当前已初始化 Expo 项目 |
| 首发平台 | iOS App 优先，Android 次优先 | 面向留学生，先做 App，不做小程序 |
| UI 组件库 | NativeWind 或 Tamagui | Tailwind 风格，适合 AI 辅助开发；最终选型待确认 |
| 后端平台 | Supabase | 数据库、认证、Storage、Edge Functions 一体化，适合小团队 |
| 数据库 | Supabase PostgreSQL | 存储用户、食材、菜品、做饭记录等结构化数据 |
| 文件存储 | Supabase Storage | 存储冰箱照片、成品照片、菜品图片 |
| 用户认证 | Supabase Auth | MVP 可先用邮箱/OTP；微信登录不再默认成立，标记为待验证 |
| AI 能力 | Claude API | 冰箱图片识别、成品评分；API Key 只能放在 Edge Functions 环境变量 |
| 无服务器函数 | Supabase Edge Functions | 承载 AI 调用与服务端逻辑 |
| 订阅支付 | RevenueCat | 二期商业化时再接入；MVP 阶段可先预留会员字段和开关 |
| AI 辅助编程 | VS Code + Claude Code 插件 + cc switch | 已验证可用 |
| 状态管理 | Zustand | 轻量，适合 RN 项目 |
| 本地敏感存储 | Expo SecureStore | 当前 MVP 不收病史/体重，但未来如有敏感信息必须放此层 |
| 本地普通存储 | AsyncStorage | 口味偏好、设备草稿、本地未注册状态等 |

```

## 7. 工程协作与模块开发规则（长期固定）

### 7.1 分工方式

当前阶段采用：

> 先横向搭公共技术地基，再纵向按功能模块开发。

原因：数据库、services、types、Storage、Edge Functions、prompt 结构尚未完全统一。如果过早让每个人独立做完整页面，容易出现各自建表、各自查 Supabase、各自定义 prompt，后期整合困难。

### 7.2 阶段划分

#### 阶段一：横向公共技术地基

- Supabase 连接
- `.env` / `.env.example`
- 数据库表结构
- Storage bucket
- Edge Function 调用方式
- `types/` 类型定义
- `services/` 接口封装
- prompt 管理规范
- README 与协作说明

#### 阶段二：纵向功能模块

- 信息录入模块
- 冰箱识别模块
- 推荐菜谱模块
- 菜谱教程模块
- 评价与回顾模块

核心原则：

> Stitch 是 UI Blueprint，不是工程结构。页面可以按功能拆，但必须依赖统一的数据结构、services 和 AI 接口。

## 9. Services 层规则

前端页面不允许直接写 Supabase 查询。

禁止：

```ts
supabase.from('xxx').select()
```ingre

推荐：

```ts
recipeService.getRecipes()
profileService.saveUserPreferences()
fridgeService.saveFridgeItems()
aiService.recognizeFridge()
```

|---|---|

## 14. RLS 与安全规则

### 基本原则

- Supabase 表默认开启 RLS。
- 用户私有数据必须带 `user_id uuid references auth.users(id)`。
- 用户只能读取、写入、更新、删除自己的数据。
- 公共菜谱库可允许匿名或登录用户读取。
- `health_check` 只用于开发验证，不作为业务表安全模板。
- 不允许把 service role / secret key 放进前端。

### 私有表示例规则方向

```sql
-- 仅示意，正式 migration 前需逐表确认
create policy "Users can read own rows"
on public.some_user_table
for select
to authenticated
using (auth.uid() = user_id);
```
